# ISSLive and NASA OEM source verification

Verified on **2026-09-28 UTC**. This file preserves the ISSLive diagnostic and NASA OEM evidence; the [NASA SSCWeb verification](sscweb-verification.md) preserves the earlier first-source decision; [current GP verification](orbital-elements-verification.md) establishes the revised first orbital-element source. The machine-readable evidence ledger is [source-registry.yaml](source-registry.yaml). `VERIFIED` means that the facts required for the stated use are supported; `PARTIALLY_VERIFIED` means a named integration fact is missing; `UNVERIFIED` means evidence is insufficient; `UNAVAILABLE` means evidence shows the datum was unavailable through the stated source during the stated observation. A connected transport is not proof that current telemetry values are flowing.

## Decision for the first backend slice

**No ISSLive realtime parameter is `READY_FOR_IMPLEMENTATION`. ISSLive integration gate: `BLOCKED_BY_PUBLIC_SOURCE` (current observation, not a permanent-outage finding).** The Lightstreamer server and subscriptions work, but the official demo and the differential Java diagnostic below received no item payloads. The provider dictionary establishes candidate identifiers and some meanings; it does not establish current value delivery, the `Value`/`CalibratedData` relationship, source time semantics, or the meaning of status codes. The minimal **candidate** for a later live check is `USLAB000058` (cabin pressure, dictionary unit `PSI`), followed by `NODE3000005` (urine tank quantity, `PCT`) only if a second non-orbital value is useful. Neither is an approved production mapping yet. No semantic internal identifier is assigned to a partially verified live item.

This is a current ISSLive gate, **not** a finding that NASA has permanently withdrawn public telemetry or proof of an upstream loss-of-signal state. MISSION1 will not wait indefinitely for this bridge: the separately verified [CelesTrak GP element source](orbital-elements-verification.md) is the first orbital implementation input for locally computed current state. [NASA SSCWeb](sscweb-verification.md) remains a secondary TLE-derived ephemeris reference, not live telemetry or measured position. NASA's OEM is a distinct predicted trajectory product for a later phase.

## Focused live differential, 2026-09-28 UTC

The **current default branch** of Lightstreamer's [ISSLive JavaScript client](https://github.com/Lightstreamer/Lightstreamer-example-ISSLive-client-javascript/tree/cb0ce84f6ad2b29aa532c26d33e292ef3283e6d5) was inspected at commit `cb0ce84f6ad2b29aa532c26d33e292ef3283e6d5`. In [`lsClient.ts`](https://github.com/Lightstreamer/Lightstreamer-example-ISSLive-client-javascript/blob/cb0ce84f6ad2b29aa532c26d33e292ef3283e6d5/src/app/lsClient.ts) it constructs `LightstreamerClient("https://push.lightstreamer.com", "ISSLIVE")`, installs a status listener, calls `connect()`, and initially requests unlimited client bandwidth. In [`Subscriber.ts`](https://github.com/Lightstreamer/Lightstreamer-example-ISSLive-client-javascript/blob/cb0ce84f6ad2b29aa532c26d33e292ef3283e6d5/src/app/Subscriber.ts) it creates **one `MERGE` subscription per item**, requests `TimeStamp`, `Value`, `Status.Class`, `Status.Indicator`, `Status.Color`, `CalibratedData`, snapshot `yes`, and max frequency `unlimited`; it attaches its `DynaGrid` listener before calling `subscribe()`. It does **not** name a Data Adapter or force a transport. Its default items are `TIME_000001`, `AIRLOCK000049`, `NODE3000005`, `NODE3000008`, `NODE3000009`, `S0000005`, `AIRLOCK000005`, and `P1000003`. The grid handles visual updates; the status listener handles **Lightstreamer connection** status, not ISS signal status. The example configures `WARN` logging and does not expose a separate item-status decoder.

The [official Space Station Telemetry demo](https://demos.lightstreamer.com/ISSLive/) was observed in a browser from **11:25:01 to 11:30:16 UTC**. Its console recorded `CONNECTING`, subscriptions for all eight default items, then `CONNECTED:WS-STREAMING` at **11:25:02 UTC**. The provider dictionary loaded and the symbol rows appeared. Every default item's **Time** and **Value** remained `-` through the final check, including `TIME_000001` and `NODE3000005`. The demo does not display the requested status fields as an upstream-feed indicator. Browser protocol frames were not exposed by the available browser inspection tool, so this is a DOM/console observation, corroborated independently by the Java wire-protocol trace below. There was **no demonstrably receiving demo item** available to use as a control. The connection indicator cannot be read as NASA/ISS signal availability.

An experimental Java 21 diagnostic under `/tmp/mission1-live-probe/` used the [official Java SE SDK 5.3.3](https://lightstreamer.com/sdks/ls-javase-client/5.3.3/api/index.html) with `DEBUG` logging. At **11:28:14–11:28:55 UTC** it connected to the same URL/application, registered client and subscription listeners before the corresponding operations, called `connect()` before `subscribe()`, requested unlimited bandwidth and frequency, snapshot `yes`, and left transport negotiation automatic. It stayed alive for 40 seconds. The SDK selected **`CONNECTED:WS-STREAMING`**, with server `CONOK`, `CONS,unlimited`, and **11 `SUBOK`/`CONF` pairs**. The wire trace recorded requests with `LS_mode=MERGE`, `LS_snapshot=true`, the expected item IDs and exact field schemas; there were no `SUBSCRIPTION_ERROR` callbacks or protocol errors. It received repeated protocol `PROBE` keepalives but **no item `UPDATE` frame or `onItemUpdate` callback**. The `SUBOK` results prove the server accepted those schemas; they do not prove every requested field would eventually contain a non-null value. The [SDK's `onEndOfSnapshot` callback](https://lightstreamer.com/sdks/ls-javase-client/5.3.3/api/com/lightstreamer/client/SubscriptionListener.html) is documented for `DISTINCT`/`COMMAND`, not `MERGE`, so its absence is not evidence of a failed snapshot. A requested `MERGE` snapshot may be absent when no current state is available; the [current Lightstreamer concepts guide](https://lightstreamer.com/ls-server/latest/docs/General%20Concepts.pdf) also notes that suppressing a `MERGE` snapshot can delay the first client event despite a snapshot request.

No raw event exists from which to decode `TimeStamp`, classify source quality, or verify `Value` units. Local UTC receipt time was recorded for callbacks and protocol events, but no telemetry receipt time exists.

### Symbol dictionary and field semantics

The [provider-maintained `PUIList.xml`](https://github.com/Lightstreamer/Lightstreamer-example-ISSLive-client-javascript/blob/cb0ce84f6ad2b29aa532c26d33e292ef3283e6d5/src/assets/PUIList.xml) (Git blob `89fbc0387e4f9b210e7f3967c0fff32e8f7ed68d`, latest repository commit dated 2023-09-20) contains **298 unique `Public_PUI` values in 15 discipline groups**. Its categories include EVA, ETHOS, CDH, ADCO, TOPO, and other console groupings. Prefix counts are `USLAB` 102, `AIRLOCK` 58, `S` 40, `NODE` 29, `P` 27, `RUSSEG` 25, `Z` 15, and `TIME` 2. An entry contains `PUI`, `Public_PUI`, `Description`, `MIN`, `MAX`, `OPS_NOM`, `ENG_NOM`, `UNITS`, `ENUM`, and `Format_Spec`. Public IDs are opaque strings such as `USLAB000058`; prefixes should not be treated as proven module ownership. `PUI` itself is the placeholder `***nOt*aVaiLable***` in examined entries. The file is **Lightstreamer-maintained provider metadata**, not an independently authenticated NASA telemetry dictionary; its age and internal inconsistencies require field-level caution. Identifier stability and revision policy are undocumented. The complete dictionary is deliberately not imported into MISSION1.

The subscription field names are **VERIFIED** from provider code, but their telemetry semantics are **PARTIALLY_VERIFIED**:

- `Value`: the example renders it as the displayed value; without a delivered sample or field specification, its numeric encoding and relationship to the dictionary's `UNITS` are unconfirmed. A dictionary `UNITS` entry is **not yet a verified unit for the streamed `Value`**.
- `CalibratedData`: present in the field list; no authoritative definition or conversion rule was found. Never assume it is the engineering-unit value or interchangeable with `Value`.
- `TimeStamp`: present and displayed after dividing a numeric value by 24 in the example. That display logic does **not** establish a UTC epoch, time scale, measurement-time meaning, or linkage between independently updated items. `TIME_000001` is labeled “Greenwich Mean Time (GMT)” with `UNITS=MS`, and `TIME_000002` is “Year” with `UNITS=YR`; how to combine them with item `TimeStamp` is unverified. `USLAB000102` is labeled “State vector time tag” with `UNITS=S`, but its epoch/time scale is unverified.
- `Status.Class`, `Status.Indicator`, `Status.Color`: field existence is verified; source-defined value vocabulary, validity rules and whether they apply to every item are **UNVERIFIED**. None is mapped to a MISSION1 quality state.

For all live candidates, **source measurement time = UNKNOWN; source publication time = UNKNOWN; Lightstreamer update time = UNKNOWN** as an absolute instant. Only MISSION1's future callback receipt time could be recorded confidently as `RECEPTION_TIME`. No callback was received in the probes, so there is no sample receipt time yet. A reception-time-only implementation could state when MISSION1 received a value, not when the ISS measured it. `GOOD`, `STALE`, `NO_DATA`, `INVALID`, `OUT_OF_RANGE`, and `UNKNOWN` remain **MISSION1-computed assessments**; the source has not been shown to publish those semantics. A connected but silent bridge is a separate operational state and must not be rendered as live telemetry.

## Source B: NASA ISS Orbit Ephemeris Message

NASA's current [Spot the Station trajectory section](https://www.nasa.gov/spot-the-station/) identifies the ISS Trajectory Operations and Planning Officer (TOPO) at Johnson Space Center as the ephemeris producer and links the current [TXT](https://nasa-public-data.s3.amazonaws.com/iss-coords/current/ISS_OEM/ISS.OEM_J2K_EPH.txt) and [XML](https://nasa-public-data.s3.amazonaws.com/iss-coords/current/ISS_OEM/ISS.OEM_J2K_EPH.xml) files. Both endpoints returned HTTP 200 on 2026-09-28 and had `Last-Modified` on 2026-09-25. The current files declare CCSDS OEM version 2.0; the official page calls this the CCSDS Orbit Ephemeris Message standard. **Use the files for units:** the XML explicitly labels `X/Y/Z` as `km` and `X_DOT/Y_DOT/Z_DOT` as `km/s`. The current NASA page has an apparent typo describing position as “kilometers per second”; its own files resolve that conflict. The former `spotthestation.nasa.gov/trajectory_data.cfm` page returned HTTP 404 on this verification date and is not a current source URL.

**Classification: `PREDICTED / EPHEMERIS`, `VERIFIED`; recommended MVP3.** NASA describes a **predicted trajectory**, updated approximately three times weekly because drag causes its prediction to accumulate error. The page describes 15 days of state vectors at four-minute intervals, with two-second spacing during reboosts. A past-dated state in a published file remains an ephemeris point; the file is not a stream of actual measured ISS positions. The current file spans `2026-09-25T16:57:11.697` through `2026-10-10T16:57:11.697` UTC, with creation date `2026-09-25T21:34:03.088` in TXT. The older publication date relative to today's date does not change NASA's approximate update-cadence statement into an SLA.

The TXT metadata identifies `OBJECT_NAME=ISS`, `OBJECT_ID=1998-067-A`, `CENTER_NAME=Earth`, `REF_FRAME=EME2000`, and `TIME_SYSTEM=UTC`; the XML corroborates these fields. NASA's page calls the frame “Mean of J2000 (J2K)”; **use the file's explicit `EME2000` identifier in any future parser** and verify the Orekit frame mapping before transformation. The header also includes mass (kg), drag area (m²), drag coefficient, first/last ascending-node details, and a trajectory event summary. NASA says the event listing may include reboosts and visiting-vehicle events; reboost periods receive denser sampling. Metadata can vary by file and must be parsed rather than assumed. The file is replaced at stable `current/` URLs; retain file creation and fetch times and do not treat the URL as an immutable version. Source publication time is not explicitly supplied; HTTP `Last-Modified` is a separate transport metadata value. NASA explicitly supplies the product for general public use and asks users to monitor its page for format changes. No pointwise covariance/accuracy guarantee is asserted here.

The verified OEM field set and proposed **provider-independent** semantic IDs are in the registry. These IDs name **predicted** quantities. The epoch is a state-vector coordinate, not a separate realtime telemetry parameter. OEM is useful later for a clearly labeled future track and independent orbital validation; it does not provide the queryable SSCWeb position contract or unblock ISSLive streaming.

## Java integration and quality contract

The [official Java SE SDK 5.3.3 guide](https://lightstreamer.com/sdks/ls-javase-client/5.3.3/api/index.html) specifies Maven artifact `com.lightstreamer:ls-javase-client:5.3.3`, Java 8+, server compatibility from 7.4.0, Apache 2.0 SDK license, asynchronous callbacks, recovery and resubscription. The observed public server identified itself as version 8.0.0. A throwaway Java 21/Maven probe used `new LightstreamerClient("https://push.lightstreamer.com", "ISSLIVE")`, a `MERGE` subscription to `USLAB000058`, the six example fields and snapshot `yes`; it reached `CONNECTED:WS-STREAMING` and received `onSubscription`. Thus **a custom Java source adapter can connect and subscribe**. An absent value callback means payload ingestion remains gated. The public provider's adapter set is not locally distributable; the client SDK's Apache license is separate from any server/feed usage conditions. No provider uptime, telemetry redistribution license, or production SLA was found; verify intended use terms before public deployment.

For a future adapter, keep raw field strings and the verified source ID at the boundary. Attach `receivedAt` from the MISSION1 clock if an update arrives; retain raw `TimeStamp` and status strings without pretending to decode them. `NO_DATA` is the honest current state when nothing arrives. A disconnected or silent bridge is platform feed health, never an ISS alarm. Any freshness threshold would be a configurable **MISSION1 policy** after observed update behavior, and reception-time freshness cannot prove measurement freshness. Do not map `Status.Class`/`Indicator`/`Color` into `GOOD` or `INVALID` without provider semantics.

## Architecture impact and next evidence gate

The accepted [V1 architecture](../architecture/02-architecture-baseline-v1.md) and [ADR-0001](../adr/0001-single-backend-and-in-process-pipeline.md), [ADR-0002](../adr/0002-postgresql-for-initial-history.md), and [ADR-0003](../adr/0003-verified-source-mapping-and-value-semantics.md) still hold. Their source-adapter boundary allows CelesTrak GP element acquisition and in-process Orekit propagation under [ADR-0004](../adr/0004-local-gp-propagation-for-current-orbit.md), without changing backend deployment or data-ownership decisions. The specification's example torr pressure and assumption that an ISSLive J2000 vector is immediately usable are corrected **here**, not in an ADR: those were unverified examples, not accepted decisions. No ISSLive production mapping is activated by this report. Orekit belongs to the separately verified GP propagation path described in ADR-0004.

The **one unresolved ISSLive blocker** is a real payload from at least one public item. Reactivation requires a bounded Java capture of raw `Value`, `TimeStamp`, status fields and local receipt UTC, plus credible meaning and unit treatment; provider confirmation of bridge/feed health or a currently publishing control item would help. Do not mark `NODE3000005` as NASA-verified or convert `USLAB000058` from PSI until the streamed `Value` representation is established. This does not block the GP element path or SSCWeb's secondary contract.

The **next single implementation task** is the CelesTrak GP/TLE + deterministic Orekit backend bootstrap described in the [roadmap](../architecture/03-repository-and-roadmap.md). This file does not authorize depicting SSCWeb ephemeris or locally propagated position as live onboard ISS telemetry. The NASA OEM and ISSLive integrations remain later, independent tasks.
