# PostgreSQL orbital-element-set history

This MVP1 storage boundary persists **validated source-provided GP/TLE sets**, not propagated orbital states. It implements the PostgreSQL choice in [ADR-0002](../adr/0002-postgresql-for-initial-history.md) using Spring JDBC for explicit mapping and Flyway for reproducible migrations. Plain Spring JDBC keeps two small tables and their upsert/order rules visible; Spring Data JDBC would add aggregate mapping without a current benefit, and JPA's entity lifecycle is unnecessary for this immutable-ish source record. The domain record has no persistence annotations. This is an implementation choice within ADR-0002, so that ADR needs no change.

`backend/src/main/resources/db/migration/V1__orbital_element_history.sql` creates two tables:

- `orbital_element_sets`: internal `bigint` ID; ISS catalog number `25544`; format `TLE`; exact raw lines; queryable element epoch; provider, upstream origin, source URI, optional publication time, SHA-256 and `SOURCE_PROVIDED_ORBITAL_ELEMENTS` classification. `(provider, catalog_number, sha256)` is unique. SHA-256 hashes `line1 + "\n" + line2` in the established parser. Epoch is stored even though Orekit can derive it because the latest/history queries order by that source time. The table has an epoch index.
- `orbital_element_observations`: `(element_set_id, retrieved_at)` primary key, with a foreign key to the source set. Every distinct successful retrieval time is retained; repeating the same TLE at the same retrieval instant is idempotent. The primary key supports each set's latest-observation lookup.

A single row with mutable first/last retrieval times would serve today's current-quality evaluation, but it would erase intermediate observations. The second narrow table preserves what MISSION1 actually saw without duplicating the raw TLE or building a general source-health event system. `element_epoch` describes the source solution; `retrieved_at` is MISSION1 observation time; `published_at` is nullable because the current CelesTrak TLE response provides no verified publication timestamp. PostgreSQL stores these as `timestamptz`; writes reject instants finer than its microsecond precision instead of silently rounding. No `GOOD`/`STALE` status is stored, because that changes with evaluation time.

`storeIfNew` revalidates raw lines, ISS catalog identity, epoch and hash, then inserts the set and retrieval observation in one transaction. PostgreSQL uniqueness, not a prior `exists` check, resolves concurrent duplicates. An existing identity with conflicting immutable metadata fails explicitly. Ordinary repeated retrieval returns the existing ID and records a new observation time when distinct. A database write or mapping error is surfaced.

`findById` and `recent(limit)` reconstruct `OrbitalElementSet` with its **latest recorded retrieval**. `recent` orders distinct sets by element epoch descending, then their latest retrieval descending, provider ascending and hash ascending; limits are 1–100. `latestUsable(asOf)` considers only sets with `element_epoch <= asOf` and at least one observation with `retrieved_at <= asOf`. It chooses the greatest element epoch, then latest eligible retrieval, then provider and hash. This means “newest observed validated orbital solution available at that time,” not most recently inserted row. It may return a stale set; the separate `orbital-current-v1` policy determines quality at evaluation time. An earlier `asOf` reconstructs the latest observation known by then.

The repository does not fetch, schedule, propagate, expose REST, or persist one-Hz positions. A later application service can connect `CelesTrakOrbitalElementsSource.fetch()` → `storeIfNew()` and, independently, `latestUsable(now)` → quality evaluation. No live source is called by database tests.
